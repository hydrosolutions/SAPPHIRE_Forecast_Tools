## Summary

P1c is a **no-new-code** phase. Snow HS/SWE/ROF migration uses the existing
`bin/initialize_snow_history.sh` wrapper — operationally validated on TAJ
2026-06-04, and ported onto the integration branch `develop_migration_toolkit`
via sibling PR #347. P1c's deliverable is the §5.3 section of
`doc/prod/update_data_migration_runbook.md` plus this gi_draft. No new wrapper,
no new tests, no edits to the snow wrapper itself.

The phase exists in the architecture plan's dependency graph
(`update_migration_toolkit_architecture.md:279`) because every data family
needs a runbook section even if it reuses a pre-existing wrapper, and because
the snow wrapper's status as the architectural precedent
(architecture §Q1, §Per-Data-Type Strategy Table row "Snow HS/SWE/ROF raw
values") needs operator-facing documentation that matches the format of the
other P1 sections.

## Context

### Architectural precedent

The snow wrapper predates the rest of the update-migration toolkit. It is the
proven minimal-non-null-payload precedent that all later wrappers (P1a runoff
DAY, P1b meteo T/P, P3 hydrograph DAY) imitate. The architecture plan §Q1
locks its status as an exception to the new P0 helper conventions:

> Exception: keep the verified `bin/initialize_snow_history.sh` embedded
> helper unchanged unless a future snow-specific PR has a reason to refactor
> it; the snow script was already verified operationally and should not be
> churned as part of v2.

Per-Data-Type Strategy Table row for `Snow HS/SWE/ROF raw values`
(architecture line 52):

## Problem

Without §5.3:

1. The runbook has §5.1 and §5.2 sections for the other CSV-source data
   families but jumps from §5.2.6 directly to §6 (laptop local-export). An
   operator following the runbook end-to-end would have no documented path
   for snow CSV migration.
2. The architectural exception (snow does not consume the P0 helpers and
   does not honor `--station-filter`) is invisible to operators. Without it
   documented, a future operator may file a bug or attempt to add the
   `--station-filter` flag, churning the verified wrapper.
3. The snow stats / norms regenerate boundary is invisible. Operators may
   attempt to migrate snow stats through the CSV path, which would fail
   silently (the wrapper sends only `value`) and then need debugging.
4. The CI gating status of the snow wrapper is not surfaced to operators.

## Desired Outcome

After P1c merges to `develop_migration_toolkit`:

- `doc/prod/update_data_migration_runbook.md` contains §5.3 covering:
  background (CSV layout, what the wrapper does), the canary single-station
  run (dry-run + full + verification SQL), the snow stats / norms boundary
  (regenerated by P6, not by this wrapper), the forward-contract note (P0
  helper exemption per architecture §Q1; `--station-filter` not honored), and
  the CI gating status.
- `bin/initialize_snow_history.sh` is unchanged (verified by `git diff` —
  P1c does not touch the wrapper).
- `shellcheck -x bin/initialize_snow_history.sh` reports zero findings.
- The pre-commit `koalaman/shellcheck-precommit` hook and the
  `shellcheck_migration_scripts` CI job both include the snow wrapper in
  scope (verified by static-config review of `.pre-commit-config.yaml` and
  `.github/workflows/build_test.yml`).
- This gi_draft is filed and a PR is open against `develop_migration_toolkit`.

## Out of Scope

- **Modifying `bin/initialize_snow_history.sh`** — architecture §Q1
  explicitly exempts the snow wrapper from the P0 helper conventions.
- **Snow stats / norms migration** — covered by P6 regenerate hook
  (`bin/backfill_snow_stats_history.sh`); architecture §Q10.
- **Harmonization with P0 helpers** (`umh_resolve_image`,
  `umh_acquire_temp_workspace`, etc.) — future refactor; out of scope here.
- **`--station-filter` for snow** — the snow wrapper does not honor the P0
  forward-interface contract; operator filters at input-data level if a
  sub-station canary is needed.
- **New tests for the snow wrapper** — wrapper was operationally validated
  on TAJ 2026-06-04 with ~157k records per snow_type across 17 stations
  (see commit message of `2c87529`); P1c does not add coverage.
- **Re-running the snow migration on any deployment** — Charter §3 forbids
  sub-orchs from running migration scripts against real DBs (canary or
  production).
