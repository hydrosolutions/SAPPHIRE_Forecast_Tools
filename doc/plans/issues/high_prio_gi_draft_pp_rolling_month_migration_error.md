# High prio — erroneous rolling-window month forecasts imported into long_forecasts

**Status:** draft — coordination item for the postprocessing/services owner.
`sapphire/services/` is colleague-managed (CLAUDE.md Ownership Boundaries). This
documents a confirmed data-quality issue and proposed remediation; it makes no
edits to service code.

## Summary

The `long_forecasts` table holds two populations of **month** forecasts:

1. **Operational (correct):** calendar-aligned (`valid_from` = 1st, `valid_to` =
   month end), issued on the operational days — **1st** (Tajik) and **10th /
   25th** (Kyrgyz). ~608k rows (54.5%).
2. **Erroneous (to discard):** a **rolling 31-day** product — `valid_from` = the
   issue date, `valid_to` = issue date + 31 days — issued on a **5-day grid**
   (days 1/5/10/15/20/25), spanning all base models and the full 2000–2026
   archive. ~508k rows (45.5%).

Population 2 is the result of a **bad bulk migration**, not operational forecast
code. It has been confirmed as an error by the long-term modeller (he did not
produce these) and should be removed.

## Root cause (read-only evidence)

- **Proximate writer:** `sapphire/services/postprocessing/app/data_migrator.py`,
  `LongForecastMigrator.prepare_month_data` (~line 730). It reads
  `{model}_hindcast.csv` files and writes `valid_from` / `valid_to`
  **verbatim** from the CSV (lines ~774–775) with **no calendar-snapping** and
  `flag` taken straight from the file. Any non-calendar window in the source CSV
  is imported as-is.
- **Every operational/forecasting path snaps to the calendar month**, so none of
  them is the source:
  - `apps/long_term_forecasting/post_process_lt_forecast.py:483-490` and
    `:182-194` reset `valid_from`→day 1, `valid_to`→month end.
  - `apps/long_term_forecasting/calibrate_and_hindcast.py:250-254` filters to the
    single `get_operational_issue_day()` and runs `post_process_lt_forecast`.
  - `apps/long_term_forecasting/dev_code/simulate_forecasts.py` — same.
- **Fingerprint** of population 2 (5-day grid, all base models, full history,
  uniform 31-day spans) matches a historical hindcast generated by the upstream
  standalone `hydrosolutions/long-term-forecasting` library (pure-CSV, no
  calendar-alignment logic) that was then bulk-imported through the migrator
  above.

The checked-in migration fixture
(`apps/iEasyHydroForecast/tests/fixtures/migration_csv/long_forecast/GBT_hindcast.csv`)
shows the *intended* clean format (`date=2024-01-22`, `valid_from=2024-02-01`,
`valid_to=2024-02-29` — calendar-aligned), confirming the rolling rows came from
out-of-spec source CSVs, not the intended format.

## Impact

- Inflates the month archive ~2× with unscoreable forecasts (a rolling 31-day
  window has no matching calendar-month norm or calendar-month observed value).
- `forecast_skill_eval` already excludes them (calendar-alignment + an
  operational issue-day filter), so eval results are unaffected once that filter
  ships. But any other consumer that treats all `long_forecasts` month rows as
  operational will be wrong.

## Proposed remediation (for the owner to decide)

1. **Delete** population 2 from `long_forecasts`: month rows whose `valid_from`
   is not the 1st of its month OR `valid_to` is not that month's last day
   (equivalently, span ≠ calendar month). Verify counts before/after.
2. **Guard the migrator:** in `LongForecastMigrator.prepare_month_data`, reject
   or calendar-snap any record whose `valid_from`/`valid_to` is not a clean
   calendar month, and log the count dropped — so a future re-run cannot
   reintroduce rolling windows.
3. Re-check **quarter** and **season** long-forecast rows for the same defect
   (not yet investigated here).
